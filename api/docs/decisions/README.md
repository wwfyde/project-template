# 设计决策记录

ADR（Architecture Decision Record）记录具有长期影响的设计选择。它说明为什么作出选择以及代价；当前接口和操作说明仍放在各专题文档中。

## 什么时候需要写？

改变资源隔离边界、身份定义、核心表关系、主要存储、跨系统事务策略、执行生命周期或公共兼容策略时，通常值得记录。

普通重命名、局部 bug 修复或容易撤回的实现细节，不必各写一篇 ADR。若后续设计推翻已实施决策，新增一篇并建立替代关系，保留旧记录解释历史数据和代码。

## 推荐模板

```markdown
# NNNN. 决策标题

状态：提议 / 已实施 / 被 NNNN 替代

## 背景与约束
当前遇到了什么问题？必须兼容哪些数据、接口或运行条件？

## 决策
选择什么？适用范围是什么？

## 考虑过的方案
各方案的收益、代价及未采用原因是什么？

## 结果与代价
哪些事情更容易了？增加了什么复杂度？哪些问题仍未解决？

## 迁移与验证
已有数据、调用方和部署如何过渡？由哪些测试证明？

## 重新评估条件
什么业务或规模变化出现后，应重新讨论此决策？

## 依据
链接实现、迁移、测试和相关决策。
```

不要把“提议”写成“已实施”，也不要把补录代码现状描述成已经完成正式架构审批。
